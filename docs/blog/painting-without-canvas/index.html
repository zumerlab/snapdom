Painting without a canvas element

And a couple of other things that fell out of giving a screenshot library a plugin system with two hooks: afterClone and afterRender.

Juan Martin Muda · July 21, 2026 · Historical API examples. In v3, eligible captures can be reused; the stateful plugins here request fresh work. The default export URL is SVG, and the current plugin guide supersedes the cache options shown below.

TL;DR

SnapDOM captures a DOM subtree by cloning it, serializing the clone to an SVG <foreignObject>, and rasterizing that. Its plugin hooks fire on every capture from the same closure, so a plugin can hold state across calls that the library never persists. Three demos built on that: a paint app with no <canvas> element, a contenteditable box rendering through WebGL, and a shooting gallery that uses the same trick as the paint app.

The setup

SnapDOM (@zumer/snapdom) is a browser library that clones a DOM element, inlines its computed styles, images and fonts, serializes the clone into an SVG data: URL, and rasterizes that to PNG, Canvas or whatever you need. Same family as html2canvas or dom-to-image, minus a few years of bitrot.

Less common is the plugin system: lifecycle hooks (beforeSnap, afterClone, afterRender, beforeExport, afterExport, plus defineExports for registering new output formats) that fire on every capture with a mutable context object. We added it for the boring reasons: watermarking, redaction, format conversion. Then we started poking at what else two of those hooks could do.

The common thread below: a JavaScript closure survives between calls, and SnapDOM's rendering pipeline is stateless by design (every capture re-clones the live element and forgets it when done). A plugin sitting between those two facts can remember things the library never will.

Painting without a <canvas> element

The paint demo looks like a normal freehand painting widget, with no <canvas> behind it. There is one hidden <div> holding an empty SVG layer, and an <img> replaced on every stroke with a fresh snapdom.toPng() result. The "canvas" is a screenshot library capturing the same tiny element over and over, each time with one more stroke baked in.

Two hooks and one closure variable:

// Trimmed to the two hooks that matter — full version, with stroke
// smoothing and SVG path bookkeeping, is at the link above.
function createPaintPlugin () {
  let savedClone = null
  let pendingStroke = null

  return {
    name: 'paint',
    recordStroke (pathData) { pendingStroke = pathData },
    afterClone (ctx) {
      // Instead of letting SnapDOM clone the pristine source, hand back
      // whatever we saved last time — with the new stroke appended.
      if (savedClone) ctx.clone = savedClone.cloneNode(true)
      if (pendingStroke) appendPath(ctx.clone, pendingStroke)
    },
    afterRender (ctx) {
      // Checkpoint what was actually rendered as the new baseline.
      savedClone = ctx.clone.cloneNode(true)
      pendingStroke = null
    }
  }
}

// on every point added while dragging:
plugin.recordStroke(pathData)
await snapdom.toPng(hiddenSource, { plugins: [plugin] })

Every stroke: append a point to an SVG path, call snapdom.toPng(el, { plugins: [plugin] }) again. afterClone swaps in last time's clone instead of a fresh one and adds the new bit of path; afterRender keeps the result. The live source element is never touched; the picture lives in the plugin's closure. Throttle to a capture every ~120ms while dragging (with a local, SnapDOM-free SVG path for cursor feedback) and it's a usable paint app that is, structurally, a loop of independent screenshots.

A roundabout way to draw a picture, and that's the point. Nothing about SnapDOM's job (clone, serialize, rasterize) changed; a plugin gave the loop somewhere to keep its memory.

A text field that's secretly WebGL

The second demo looks and behaves like a normal editable text field: real caret, real selection, paste works, Enter inserts a newline. None of the visible text is painted by the browser's text engine. Underneath is a WebGL <canvas>, and what you read is a texture.

Two DOM elements make this work. A transparent contenteditable proxy sits on top of the canvas to give the browser somewhere to blink a caret and to receive keystrokes, so caret-color is set but the text is color: transparent. A second, hidden element mirrors what you typed and is the one SnapDOM captures. A plugin's defineExports adds a webgl export that feeds each capture into a double-buffered WebGL renderer, which cross-fades between old and new texture over about 110ms so nothing pops:

function seamlessWebgl (renderer) {
  return {
    name: 'seamless-webgl',
    defineExports () {
      return {
        webgl: async ctx => renderer.update(ctx.export.url)
      }
    }
  }
}

// on every keystroke, against the hidden mirror element:
const capture = await snapdom(hiddenSource, { plugins: [plugin], cache: 'full', fast: true })
await capture.to('webgl')

ctx.export.url is the rendered PNG data URL for that capture. defineExports hands the plugin the finished render and lets it decide what "exporting" means, here "upload as a GPU texture" instead of "hand back an <img>." A shader dropdown on the page (hologram scanlines, CRT, kaleidoscope, a datamosh effect, six more) never touches SnapDOM; it samples whichever texture is already on the GPU differently. Same capture pipeline, eight different-looking outputs.

The practical caveat: every keystroke can trigger a full capture, so this stays smooth only on cheap-to-capture elements (small, no heavy fonts or images). A dirty/working flag pair coalesces bursts of fast typing into one trailing capture instead of one per keystroke, which is what keeps it usable.

Also: a shooting gallery

One more, to make a point: the target range is a ten-shot shooting gallery where every bullet hole is permanent and the target accumulates damage over a whole game. It uses the same afterClone/afterRender persistent-clone pattern as the paint app. A plugin holds the last rendered clone, appends a jagged torn-paper hole marker on each shot, and hands that back on the next capture. The live target element never gets a bullet hole; the damage lives inside the plugin.

The same two hooks doing paint accumulation and bullet-hole accumulation is the finding here: "remember the last capture and build on it" turned out to be a general-purpose primitive.

Why a screenshot library has a plugin system at all

Most of what a plugin does here could be built without one, by hand-rolling a capture-and-composite loop around snapdom.toCanvas(). The reason it's a plugin is that afterClone and afterRender sit inside SnapDOM's clone and render pipeline, with access to the intermediate state (styles, fonts, the fully resolved clone) the pipeline already computed. Hand-rolling the loop means reimplementing everything SnapDOM does to make a clone faithful (pseudo-elements, embedded fonts, CSS variables, Shadow DOM) instead of hooking two points in the middle.

The other three demos in the set are on the same page: a card that shatters, glitches, dissolves or goes holographic, a simpler single-texture version of the WebGL mirror above, and a stop-motion flipbook that uses afterRender to pull data out of a capture instead of accumulating anything. The plugin spec (PLUGIN_SPEC.md) documents the full hook order and the defineExports API used above.
